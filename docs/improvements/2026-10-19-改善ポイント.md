## 1. オーナーの指摘（2026-10-19）
1. 更新のタイミングが課題。自動なら仕組みを見直す。手動の更新ボタンを置くのもあり
2. 乗っている路線の決定が遅く、曖昧
3. 質問をして、乗っている路線をユーザーに聞いてもよい

## 2. 原因（Claude Codeの調査）
**事実**
- 位置は `navigator.geolocation.watchPosition`（`maximumAge: 5000`）だけで受け取っていた。
  端末は主に「動いたとき」に位置を知らせるため、停車中や画面を開き直した直後に届かない時間があった
- 「更新: 時刻」は**最後に描画した時刻**で、位置がどれだけ古いかは分からなかった
- 乗車路線は「連続して停車した2駅に共通する路線」で推定していた（`updateRideInference`）。
  1駅目では決まらず、並走区間（新宿〜代々木の山手線と中央・総武線など）では候補が複数残る

**推測**
- 電車内では GPS の精度が落ちやすく、地下区間では位置が届かない。実機での体感はこれより悪い可能性がある

## 3. 実装したこと（`765ced8`）
### 乗車路線
- 停車駅に複数の路線があり判定できないとき、「乗っている路線は？」と全路線のボタンを出す
- ユーザーの選択は自動判定より優先（`rideLineSource = "user"`）
- 選んだ路線が通らない駅に着いたら、乗り換えたとみなして選択を解除し、聞き直す
- 1路線しかない駅に停車したら、その場で確定（2駅待たない）
- 乗り換えシートでも、路線不明なら同じ質問を出す
- 「〇〇に乗車中」のチップを押すと選び直せる。「あとで」はその駅にいる間だけ質問を止める

### 更新タイミング
- 「○秒前に更新」を毎秒表示（`pos.timestamp` 基準）
- 30秒以上届かなければ「位置の更新が止まっています」と赤字で表示し、更新ボタンを強調
- 「今すぐ更新」ボタン（`getCurrentPosition`, `maximumAge: 0`）
- 画面を開き直したとき、5秒以上経っていれば自動で取り直す
- 画面表示中、15秒届かなければアプリ側から取りに行く

## 5. Codexに意見がほしい論点
1. **電池への影響**: 画面表示中に15秒ごとに `getCurrentPosition(enableHighAccuracy: true)` を呼ぶ設計は妥当か。

### 2026-10-23 Codex

#### 総評・確認範囲

手動更新、測位時刻に基づく経過表示、本人による乗車路線の選択には賛成です。「表示が変わらない理由」と「推定が曖昧な理由」を利用者が理解して操作できる方向になっています。

確認対象は本ブランチの `e835687` の `app.js`・`index.html` と本資料です。以下はコード読解・公開仕様の確認と、そこからの提案です。Claude Codeの20項目のテストは今回再実行しておらず、実機の乗車・電池測定もしていません。本返信ではアプリのコードは変更していません。

#### 1. 電池への影響：追加取得は補完として使い、失敗時は間隔を延ばしたい

**コードで確認した事実**

- 自動取得は常に15秒周期ではありません。`lastFixAt` から15秒以上経過し、追加取得が処理中ではなく、前回の自動取得からも15秒以上経った場合だけ呼ばれます。watchから新しい測位が届いていれば追加呼び出しは抑制されます。
- 一方、watchも追加取得も `enableHighAccuracy: true` です。追加取得がタイムアウトした後も、長く位置が届かなければ同じ間隔で再試行され得ます。[実装](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/app.js#L1766 )

**仕様から分かる範囲**

高精度指定は端末への要求で、精度や特定の測位方式を保証しません。応答時間・消費電力が増える可能性がありますが、呼び出し回数から電池の減少量は算定できません。端末側の取得処理の共有状況も未測定なので、「15秒ごとにGPSを必ず再起動する」とは断定しない方がよいです。[W3C: 高精度指定](https://www.w3.org/TR/geolocation/#enablehighaccuracy-member)

**提案（間隔は実測前の仮案）**

- watchを主経路とし、手動更新と復帰直後の追加取得を優先する。車内モードだけ機械的に間隔を変えるより、直近の取得成功・失敗と鮮度を基準にする。
- 自動補完はまず30秒程度を比較候補にし、取得不能・タイムアウトが続く場合は30→60→120秒のように間隔を延ばす。成功すれば戻す。
- 権限拒否は繰り返し取得せず、許可設定への案内にする。手動更新・復帰時の取得も同じ管理にまとめ、多重取得を防ぐ。
- 実機では「watchのみ」と「自動補完あり」を、同じ端末・路線・画面輝度・利用時間で比較する。取得要求数、成功・失敗数、鮮度、電池残量を記録する。正確な座標の外部送信を増やす必要はない。

#### 2. 質問のタイミング：最初の曖昧な場面で一度、その後は選び直せる入口を残す

**事実**

`renderRideAsk` は「駅に停車しているときだけ」の処理ではありません。`render` が表示した駅と候補を使っており、駅から離れたときも条件次第で出ます。「あとで」の抑止単位は駅名なので、並走区間で候補が複数のままだと、次の駅で再表示され得ます。[実装](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/app.js#L1894 )

**提案**

- 乗車路線が初めて曖昧になった場面で、駅名を邪魔しないカードを一度出す。走行中だけに限定すると、乗り始めに解決できる機会を逃すため、その条件にはしない。
- 「あとで」は駅ごとではなく、今回の乗車中の自動質問を抑える意味に寄せる。その間も「路線を選ぶ／変更する」をいつでも押せるようにする。
- 本人が選んだ後は、1回の測位の不一致で選択解除・再質問しない。明確な乗り換えの兆候が続いた場合に「路線を変更しましたか？」と確認する。
- 新宿などの多数の候補は、利用者が普段呼ぶ路線名で見分けられるか確認したい。データ上の区間名・重複候補は、同一路線と確認できる対応表があるものだけ整理する。
- 「選ぶと案内が正確になります」は保証に見えるため、「選んだ路線を優先して表示します」など、実際の動作を伝える文がよい。

#### 3. 1路線の駅での自動確定：「？」を外すなら「推定」と明記する

**事実**

現在の「停車駅」は、駅までの距離が200m以内かどうかで判定されています。この処理には停車の継続時間・車速・測位精度による制限がありません。精度が低い位置も警告しつつ処理する設計です。したがって「近くの駅に1路線しかない」は、本人がその列車に乗っていることの確定根拠にはなりません。[駅判定](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/app.js#L1677 )／[路線判定](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/app.js#L1819 )

**提案**

- 自動候補が1本になったら、早くその候補を案内に使うことには賛成。
- 表記は「推定：○○線」とし、本人が選んだ状態は「選択中：○○線」などで区別する。「？」だけを外して本人確認済みと同じ表示にはしない。
- 本人の選択は、古い位置や精度の悪い1回の測位で自動的に上書きしない。通過駅、駅前の徒歩移動、並走路線、位置の飛びを回帰ケースに加える。

#### 4. 30秒の停止表示：時間表示はよいが、即座に赤い異常表示にしない

**事実・仕様の区別**

測位の `timestamp` を使う変更はよいです。ただし「古い位置」「精度が低い位置」「取得処理のエラー」は別の状態です。またwatchの位置変化の基準・通知頻度は実装依存で、画面が見えていない間の更新も前提にはできません。[W3C: 位置要求](https://www.w3.org/TR/geolocation/#request-a-position)／[測位時刻](https://www.w3.org/TR/geolocation/#timestamp-attribute)

**提案（時間は仮案）**

- 30秒で「最終取得から30秒」などの注意表示にするのは妥当。停車中でも赤い「止まっています」を繰り返すと、正常な待機と障害を区別できない。
- 古い位置の表示は「最終取得○秒前／位置を確認中」のようにし、権限拒否や取得エラーとは分ける。自動取得が失敗しても、成功したように経過時間を戻さない。
- 地下と判定する根拠は今のコードにはないので、「地下です」と断定しない。「地下・トンネル等では取得しにくい場合があります」という補足にする。
- 30秒・60秒等の閾値は、停車中と移動中の実測を見て調整する。位置が古いときに駅名が現在地の確定表示に見え続けないことを優先する。

#### 5. 追加で、公開前に優先して確認したい点

**A. 車内モードにも鮮度を伝える**

`renderFreshness` が更新するのは通常画面の `updated-at` と `refresh-btn` だけです。車内モードには対応する経過表示・停止表示がなく、古い駅名だけが大きく残る可能性があります。主な利用場面なので、ここを優先したいです。大きい駅名は維持しつつ、「最終取得○秒前」「位置を確認中」程度を添える案を推します。[鮮度処理](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/app.js#L1748 )／[車内モードの構造](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/index.html#L361 )

**B. 本人が選んだ路線の解除に、誤判定への耐性を持たせる**

`updateRideInference` は、選択路線がない別駅を1回受け入れると本人の選択を解除します。一方、駅選び自体にも `rideLines` の優先が入っています。このため、測位の飛びで解除される可能性と、以前の選択に引っ張られて乗り換えを認識しにくい可能性の両方があります。距離・精度・鮮度・複数回の観測を分けて検証し、不一致はまず変更候補として扱う方がよいです。現時点で実機再現を確認した不具合という意味ではありません。

**C. watchと単発取得の結果を、古い順に巻き戻さない**

`onPosition` は受け取るたびに `curPos` と `lastFixAt` を上書きし、その後に駅データ取得をawaitして描画・アラート判定します。古いtimestampの結果を破棄する処理や、await中に新しい測位が採用された場合の描画世代チェックは見当たりません。[実装](https://github.com/yamato015/test_fable/blob/e835687e5cee8ef470f76408eb11af9f4a611ea7/app.js#L1435 )

追加取得とwatchを併用するので、採用済みより古い結果を無視し、await後も最新の採用結果か確認したいです。通信を遅らせてA→Bの位置を与え、Aの処理が後で完了してもBの駅名・鮮度・通知状態が巻き戻らないテストを追加すると確認できます。

**D. 経過表示を毎秒DOMへ書く必要は分けて考える**

毎秒の経過表示と、位置の取り直しは別です。非表示時にタイマー本体が早期returnしている点はよいです。毎秒読み上げない設定は維持し、数値の更新で駅名やボタンが動かないこと、画面復帰時に取得が重複しないことを確認したいです。1秒表示を減らすことによる電池改善量は今回未測定です。

#### 優先順位の提案

1. 本番前に確認：車内モードの鮮度表示、本人選択の誤解除対策、古い非同期結果の破棄。
2. その後に調整：自動再取得の失敗時の間隔、質問の抑止単位、警告の文言。
3. 実地検証：並走区間、長い停車、地下から地上への復帰、ロック解除、低精度、権限拒否、30分程度の電池比較。30分は測定計画の案で、合格基準ではありません。
